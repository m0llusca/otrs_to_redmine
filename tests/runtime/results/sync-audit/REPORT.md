# Повторный аудит синхронизации 1.0.30

Дата: 2026-10-12. Исходники 18 файлов пакета и OPM остались неизменными; SHA-256 подтверждён в `source-boundary.json`. Новые варианты выполнялись только как process-local wrappers в изолированном локальном OTRS. Это анализ следующего этапа, а не новая версия установочного пакета.

## Требования пользователя

До 1000 связанных тикетов; нагрузка заметна на OTRS, Redmine отдельно не замерен. Требуется обновление сразу после изменения Redmine. **Изменять разрешено только расширение OTRS**. Webhook/плагин на Redmine не входит в предлагаемый план.

При текущих SyncBatchLimit=50 и расписании раз в 5 минут полный обход 1000 тикетов занимает около **100 минут**, не считая выполнения. Снижать задержку только учащением этого же пути дорого: каждый неизменившийся тикет продолжает менять служебный DF, историю, change_time, события и кеш.

## Самый сильный подтверждённый резерв OTRS

Настоящий `DynamicField::Backend::ValueSet` вызывает PostValueSet для Ticket: запись change_time/change_by, HistoryAdd, сброс кеша и событие. Следовательно, запись `RedmineLastSyncAt` — полноценное изменение тикета, даже при неизменившемся Redmine.

Отдельные прогоны с режимом кеша Daemon worker (`CacheInMemory=0`, `CacheInBackend=1`) и явной обработкой отложенных событий ObjectManager до завершения измерения:

| 50 неизменившихся тикетов | Текущая 1.0.30 | Эксперимент: без записи времени проверки в тикет |
|---|---:|---:|
| SQL-запросы | 1030 | 126 |
| Записи истории | 50 | 0 |
| Фактические вызовы TicketGet, включая ядро | 300 | 50 |
| CPU участка, с | 2.313 | 0.704 |
| Время участка, с | 2.987 | 0.807 |
| Пик RSS, МиБ | 79.42 | 72.45 |

Это один дополнительный прогон каждого варианта, достаточный для подтверждения механизма и количества операций в фиксированном сценарии, но не для обещания стабильного процента CPU на сервере. Подавление LastSyncAt — экспериментальная верхняя оценка экономии, не завершённая реализация переноса диагностики. В самом расширении это поле нигде не читается; внешние отчёты/настройки пользователя не проверены. Aggregate health при этом обновляется.

Прежние CPU/SQL отчёты измеряли тело вызова до окончания жизненного цикла процесса; полный вызов событий и режим кеша настоящего Daemon там отдельно не воспроизводились. Новые полные числа **не следует напрямую сравнивать** с прежними CLI-замерами. Тестовые дублёры также не показывали дополнительные вызовы TicketGet внутри ядра и событий.

## Другие свежие эксперименты

Ниже отдельная серия измерений тела метода: обычный режим CLI-кеша, отложенные события выполняются при завершении процесса и не входят в CPU/SQL таблицы. Для 1000 тикетов CronSync вызван 20 раз подряд **без пятиминутных пауз**, чтобы измерить объём работы полного обхода. Это не действующее расписание Daemon.

| Сценарий | Текущий код | Изолированный эксперимент |
|---|---|---|
| 1000 неизменившихся тикетов, одна задача | 6047 SQL, 1000 историй, 3000 TicketGet | без LastSyncAt: 2045 SQL, 0 историй, 1000 TicketGet |
| 50 различных задач Redmine | 53 TCP, 53 HTTP | reuse на CronSync: 1 TCP, 53 HTTP |
| 1000 различных задач, 20 проходов | 1003 TCP, 1003 HTTP | reuse на каждый проход: 20 TCP, 1003 HTTP |
| 10 тикетов × 1000 новых обычных HTML journals | 10000 ToAscii, 0 заметок | ранний фильтр: 0 ToAscii, 0 заметок; те же курсоры/SQL |
| 10 связанных тикетов, один недоступный файл | 10 одинаковых загрузок 404 | память ошибки внутри группы: 1 загрузка 404; все тикеты остаются retryable |
| Нет связанных тикетов, холодный кеш каталогов | 3 HTTP-запроса к каталогам формы | кандидат: вынести warming из пути sync |

Три лишних каталожных запроса в HTTP-числах относятся к **холодному кешу**. TTL каталога 900 секунд, поэтому это не три запроса в каждом штатном проходе.

Для обычных journals три повтора каждой версии дали медиану CPU 3.050 → 0.351 секунды при 0 заметок в обоих вариантах. Ранний фильтр сохранял вычисление MaxJournal; отбрасывались только journals, которые существующая семантика всё равно не переносит. При исправлении коротких статусных переходов предикат нужно строить по конкретному journal, а не конечному статусу.

### Чего пока нельзя обещать

Переиспользование HTTP надёжно уменьшило число соединений, но CPU/RSS на длинных локальных HTTP-прогонах неоднозначны. В полном 1000-тикетном массовом сценарии один прогон текущей версии дал CPU 146.438 с / RSS 93.94 МиБ, а reuse — CPU 189.680 с / RSS 133.70 МиБ. Это не доказательство причины различия, но причина **не включать расширение scope вслепую** и отдельно проверить длинный fan-out/HTTPS перед поставкой.

Удаление raw JSON из issue-cache уменьшило медианный RSS в большом журнале всего с 82.53 до 81.76 МиБ; CPU не улучшился. Заметного подтверждённого выигрыша здесь нет. Пик самого JSON-декодирования таким приёмом не ограничивается.

## Массовая полезная работа всё равно остаётся

1000 тикетов получили 1000 настоящих внутренних заметок. Тело 20 последовательных CronSync вызовов заняло 189.9 с на эмулируемом стенде, выполнило 54057 SQL, создало 7000 записей истории и сделало 18000 TicketGet. Из 5000 DF-записей — по 1000 RedmineStatus, LastJournalID, LastAttachmentSyncOn, LastUpdatedOn и LastSyncAt. Отложенные события в этот большой методный замер не включены, значит это **не верхняя оценка всего времени доставки**.

Для отдельного полного daemon-style прогона 50 настоящих заметок с обработкой событий: 6695 SQL, 350 историй, CPU 9.837 с. Масштабировать это время линейно на production нельзя, но одновременно обещать завершение всех 1000 доставок «мгновенно» без измерений тоже нельзя.

## Подтверждённый дефект коротких переходов

Новый focused probe воспроизвёл `New → Проверка решения → New` между опросами: **0 заметок, journal checkpoint=12**. Текущий WriteNote вычисляется по конечному статусу и отличию от сохранённого, а не по каждому journal. Та же логика уже есть в базовом commit до оптимизаций. Учащение опроса лишь снижает вероятность, не исправляет дефект.

Следующий обработчик должен разбирать новые status journals по ID и old_value/new_value, сопоставлять конкретный переход с StatusSync, сохраняя запрет обычных комментариев и эха. Это требуется вместе с новой схемой доставки, чтобы быстрые переходы не терялись.

## Рекомендуемый порядок

1. Перенести успешные проверки из мутаций тикета в служебную диагностику. Сохранить надёжные journal/file checkpoints. Это наиболее сильный доказанный резерв фона OTRS.
2. Убрать ненужное преобразование journals; исправить короткие переходы и защитить ручной/фоновый sync от пересечений. Не рассчитывать, что атомарность курсора равна атомарности создания заметки.
3. Мемоизировать одинаковые ошибки скачивания только внутри issue-группы; backoff/Retry-After для 429/5xx. TooLarge зависит от оставшегося бюджета конкретного тикета — простое общее кеширование некорректно.
4. Реализовать отдельный лёгкий poller расширения: пакетные списки уникальных issue ID, обработка только изменений/незавершённой доставки, постоянный outbox и ограниченные workers в существующем OTRS. Предложение подробно в [PLAN.md](PLAN.md).
5. Отдельно верифицировать reuse на больших sync/HTTPS. Убрать прогрев каталогов из критического пути, если это не ухудшает согласованную скорость открытия формы.

REST API позволяет список issue_id, закрытые задачи через status_id=* и фильтр updated_on; это подтверждено [официальной документацией Redmine](https://www.redmine.org/projects/redmine/wiki/Rest_Issues). Первоначальная достаточная схема пакетных снимков без глобального watermark проще защищает доставку. Временной фильтр — необязательное дальнейшее сокращение payload с inclusive overlap, отдельными курсорами пакетов и полной периодической сверкой.

Для 1000 **различных** задач по 100 на запрос — 10 запросов полного прохода, если целевой сервер действительно возвращает по 100 строк. Каждые 5 секунд это около **2 запросов/с**, плюс details/файлы/повторы. Это в 100 раз меньше, чем по одному GET всех 1000 каждые 5 секунд, но **больше текущего** медленного режима примерно 0.167 issue GET/с. Снижение CPU Redmine не измерено. При 1000 тикетов на одну задачу опрашивается одна задача; 1000 OTRS-доставок всё равно остаются.

[List API Redmine 6.0](https://raw.githubusercontent.com/redmine/redmine/6.0-stable/app/views/issues/index.api.rsb) возвращает description и другие данные; сужение серверного ответа до трёх полей не предполагается. Конкретные версия, payload, ограничения и CPU Redmine требуют проверки до выбора частоты. Без изменений на стороне Redmine строгая мгновенная доставка невозможна; реалистичная цель — несколько секунд на обнаружение и отдельный измеряемый срок массового fan-out.

## Проверка очереди OTRS

На настоящем OTRS 6 воспроизведено: функция вернула бизнес-ошибку, а AsynchronousExecutor вернул 1. Две постановки одинаковой задачи с MaximumParallelInstances=1 обе вернули 1, но в scheduler_task была только одна запись. Исходники SchedulerTaskWorker также подтверждают удаление задачи после исполнения. Поэтому durable pending/retry/lease — обязанность расширения; имя задачи и return boolean не являются гарантией доставки. Данные: `queue-probe.json`.

## Методика и границы

37 новых прогонов: 32 метода/прототипа, из них 26 небольших повторов и 6 одноразовых 1000-тикетных проходов; ещё 5 daemon-style прогонов с обработкой событий. Отдельно воспроизведены короткий статусный переход и две особенности Scheduler. Существующие 35 subtest не повторялись, поскольку production-код и эти тесты не менялись.

OTRS 6.0.10 CE / Perl 5.16.3 / MariaDB 10.11; amd64 под Rosetta/эмуляцией на Mac arm64, ограничение OTRS 1 CPU/1 ГиБ. Настоящие Ticket/Article/DF/DB и события. Redmine — локальный контролируемый HTTP peer. Тестовая база новая и синтетическая, internal Docker network, без опубликованных портов. Cron/Daemon/mailfetch/web-server не запущены; выбранные daemon cache/event шаги воспроизведены явно. Настоящий Redmine, его CPU и production OTRS, Znuny 7, email-доставка не проверены.

Instrumentation считает вызовы и нормализованные SQL внутри Perl, поэтому она сама входит в CPU. Малые повторы показывают разброс; большие n=1 нужны для масштаба/числа операций, не для статистически уверенного процента ускорения. Full-task измерения включают явное ObjectEventsHandle; method-only не включают финальную обработку событий/закрытие процесса. SQL нормализованы без Bind-значений; секрета API/паролей в результатах нет.

Доказательства: `raw.json`, `summary.json`, `daemon-task-raw.json`, `semantic-probes.json`, `queue-probe.json`, `source-boundary.json`. Скрипты воспроизведения: `tests/runtime/sync_audit.pl`, `sync_audit.py`, `sync_task_audit.py`, `sync_queue_probe.pl`, `sync_audit_peer.mjs`. Прототипы не являются готовым исправлением и не включены в OPM.
