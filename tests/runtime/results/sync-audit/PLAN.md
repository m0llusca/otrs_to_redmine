# Предложение следующего этапа синхронизации

Ограничения пользователя: до 1000 связанных тикетов, нагрузка заметна на OTRS; Redmine не замерен. Требуется доставка сразу после изменений. Изменять разрешено только расширение OTRS. Это предложение, не реализованное изменение пакета.

## Реалистичная цель

Без отправки событий из Redmine строгая мгновенная доставка невозможна. Цель — обнаружение за несколько секунд в штатном режиме; полный fan-out 1000 тикетам имеет отдельное время завершения. Оно зависит от HTTP, очереди, событий OTRS, БД и вложений. Пауза опроса относится к полному проходу всех уникальных issue ID, а не к одной странице.

Текущие 50 тикетов раз в 5 минут дают около 100 минут полного обхода 1000 тикетов. Учащение этого же пути одновременно учащает TicketGet, технические DF-записи, историю, события и сброс кеша.

## Схема внутри OTRS

```mermaid
flowchart LR
    A[Фоновый модуль OTRS] --> B[Redmine REST: пакеты уникальных ID]
    B --> C[Сравнение и поиск незавершённой доставки]
    C -->|Нет работы| A
    C -->|Есть работа| D[Постоянное состояние доставки в БД OTRS]
    D --> E[Штатный Scheduler OTRS]
    E --> F[Доставка порциями по 50 тикетов]
    F -->|Ошибка или продолжение| D
```

1. Один фоновый модуль расширения читает связанные issue ID и опрашивает Redmine пакетами, например по 100 ID. На первом этапе постоянная схема без глобального временного фильтра проще и надёжнее: она не зависит от глобального watermark. Хранить только небольшую проекцию id/status/updated_on; не делать TicketGet и DF ValueSet для каждого неизменившегося тикета.
2. [REST API Redmine](https://www.redmine.org/projects/redmine/wiki/Rest_Issues) поддерживает `issue_id` со списком ID и `status_id=*`. Размер пакета должен учитывать фактический `limit`/пагинацию целевого сервера. При 1000 различных задачах и 100 результатах на запрос — 10 запросов за полный проход. При 1000 тикетов на одну задачу — одна задача для опроса.
3. Изменения и локальные новые связи порождают работу в небольшом постоянном outbox расширения в существующей БД OTRS. Он хранит незавершённую доставку/версию, прогресс, попытки и lease. Наблюдённое изменение и доставленное обновление — разные состояния.
4. Обработчик использует штатные Scheduler workers, ограничивает число тикетов/время работы и возобновляется без ожидания следующего пятиминутного cron. Очередь не должна содержать копии больших JSON и файлов. Журналы/метаданные и спулы переиспользуются в ограниченной области; освобождаются на выходе.
5. При ошибках заметок/файлов outbox остаётся незавершённым. После рестарта или истечения lease работа восстанавливается. Ручной sync, Admin и Daemon должны разделять блокировку/проверку курсора, а не обходить друг друга.
6. Завершение работы версии N должно условно обновлять outbox: новая обнаруженная версия N+1 не может быть стёрта поздним завершением предыдущей работы. Блокировка и outbox сами по себе не закрывают окно сбоя между созданием article и записью checkpoint; стратегия идемпотентности обязательна до обещания доставки без дублей при аварийном восстановлении.
7. Журналы обрабатываются по ID с разбором конкретных переходов `old_value/new_value`. Объединение сигналов проверить issue допустимо, но разные переходы статуса нельзя терять. Сохраняются правила StatusSync, запрет обычных комментариев/file-only заметок/эха, отдельные курсоры тикетов и checkpoint после успешной заметки.

Дополнительный Redis, отдельный внешний сервис и изменения Redmine для этой схемы не требуются. Новые persistent данные — рабочее состояние расширения; текущий установочный пакет этим аудитом не изменён.

## Почему нельзя просто вызвать AsynchronousExecutor

Исходники настоящего OTRS 6 проверены отдельно. Executor не использует возвращаемый `Success => 0`, а SchedulerTaskWorker удаляет отработанную задачу. Следовательно, ошибка доставки сама по себе не создаёт надёжного повтора.

Ещё один крайний случай: `MaximumParallelInstances=1` с тем же именем задачи видит текущую задачу и блокирует постановку продолжения. Внутренний TaskAdd возвращает -1, а внешний Scheduler::TaskAdd воспринимает его как успех. Поэтому authority для pending/dedup/recovery должен быть outbox/lease; нельзя считать имя Scheduler-задачи и его boolean результат достаточной гарантией.

## Нагрузка Redmine и границы

Пять секунд — ориентир для проверки, а не обещание. Для 1000 уникальных задач 10 запросов раз в 5 секунд — около 2 запросов/с, 172800/сутки, плюс подробности изменённых задач, файлы и повторы. Текущий медленный режим делает около 14400 индивидуальных проверок/сутки при непрерывной работе. Пакеты намного дешевле, чем 1000 индивидуальных GET каждые 5 секунд, но не означают уменьшение нагрузки относительно нынешней задержки до 100 минут.

[Стандартный list API Redmine 6.0](https://raw.githubusercontent.com/redmine/redmine/6.0-stable/app/views/issues/index.api.rsb) возвращает также description/custom fields и другие поля; узкую server-side проекцию предполагать нельзя. Следует измерить фактические байты, CPU/SQL Redmine и p95 полного прохода на целевой версии до выбора постоянного интервала.

Если измерения покажут, что содержимое ответов дорого, фильтр `updated_on >= ...` — отдельная необязательная оптимизация: inclusive overlap, курсоры отдельных пакетов, отсутствие продвижения через ошибки/неполные страницы и периодическая полная сверка. Глобальный максимум из последней страницы способен пропустить изменение ранее опрошенной страницы. Одинаковый timestamp не доказывает отсутствие нового journal; нужны повторная проверка недавно изменённых задач и сверка journal ID.

Пропавшая из списка задача может быть недоступной или скрытой, а не удалённой. Новые связи, unlink/relink, закрытые задачи и восстановление после простоя требуют явных проверок. Массовое обновление не должно одновременно запустить 1000 Perl-процессов.

## Самый близкий самостоятельный пакет

До изменения архитектуры можно отдельно выпустить работающий пакет оптимизаций текущей схемы:

- Убрать изменение тикета ради LastSyncAt: диагностика — в служебном кеше/health, бизнес-курсоры — в надёжном хранилище.
- Отфильтровать ненужные journals до HTML/UTF-8 преобразований, сохраняя продвижение курсора. Одновременно устранить потерю коротких статусных переходов.
- Не повторять одинаковые ошибочные загрузки файла внутри одной issue-группы. Не кешировать TooLarge без учёта разных оставшихся бюджетов тикетов.
- Добавить backoff/Retry-After для 429/5xx и защёлку от параллельного sync.
- Переиспользование HTTP-соединения в sync проверять отдельно на длинных массовых операциях и HTTPS. TCP-выигрыш доказан локально, CPU/RSS — не считать гарантированным.
- Убрать прогрев каталогов формы из критического пути синхронизации, сохранив его TTL-политику/быстрое открытие формы. Сейчас это три обычных запроса только на холодном кеше, не в каждом проходе.
