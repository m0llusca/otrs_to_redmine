# Итоговое ревью OTRSRedmineBridge 1.0.30

Дата: 2026-10-12. База сравнения: `acc9175b793f405a3ce5431f382ae2da477cbf10` (1.0.29). Проверены все изменённые production-файлы, взаимодействие с неизменёнными модулями, новые тесты и содержимое OPM. Исходники остаются локальными незакоммиченными изменениями. Сервер не изменялся.

## Вердикт

Блокирующих замечаний в окончательной версии не осталось в проверенном объёме. Два независимых ревью покрыли синхронизацию/курсоры и создание задач/HTTP/вложения. Найденные регрессии исправлены до сборки окончательного пакета. Установка, обновление и проверки выполнялись только в изолированном локальном OTRS.

## Исправлено при ревью

| Проблема | Исправление и проверка |
|---|---|
| Ошибка загрузки файла или подробностей задачи блокировала mapped state OTRS | Состояние применяется независимо; заметка и курсоры сохраняют повторную попытку. Добавлены проверки details/download failure. |
| После включения SyncAttachments старый файл мог попасть в следующую статусную заметку | Отдельный DF `RedmineLastAttachmentSyncOn` отмечает просмотр потока файлов; покрыты отключение/включение, компактный GET после catch-up, монотонность и очистка при unlink. |
| FormID FileID в OTRS 6 позиционный; изменение формы во время сетевых вызовов подменяло файлы плана | Форма читается и фиксируется в спулах до сети; metadata/data сопоставляются по набору характеристик, не позиционным ID; изменение набора отклоняется. |
| Исключение чтения вложения после POST оставляло созданную задачу без локальной ссылки | Локальные границы исключений сохраняют IssueID, DF связи и предупреждение. Повторный вызов не создаёт дубль. Ошибки preflight очищают lock. |
| UploadCache FS сообщает размер меньше фактического | Стабильность reported metadata проверяется отдельно от фактических байтов; фактический бюджет проверяется до создания. Проверены 70 reported / 100 actual и настоящий FS backend. |
| Устаревшая cleanup-миграция обращалась к уже отсутствующим настройкам при upgrade | Удалён obsolete-путь; CodeUpgrade вызывает актуальную установку полей. Проверен переход 1.0.29 → 1.0.30. |

## Подтверждённая функциональность

- 3 Perl-файла / **35 верхнеуровневых subtest**, PASS. Новые регрессионные сценарии сначала воспроизводили ошибки, затем стали проходить.
- Все **15 Perl-модулей пакета** компилируются настоящим Perl 5.16.3 OTRS.
- Установленные из OPM модули загружались из `/opt/otrs`, без overlay тестируемых исходников. Ticket/Article/DF/DB — настоящие классы OTRS.
- 125 связанных тикетов обходятся страницами 50/50/25.
- Переход closed successful → open доставляет одну объединённую заметку каждому из 10 связанных тикетов и 20 файлов; повторная синхронизация не создаёт дублей.
- Бинарные байты `00ff8041` сохраняются без UTF-8-преобразования.
- Создание задачи отправляет 16 файлов по 1 МиБ с правильными SHA-256 и присоединёнными токенами.
- Дополнительный файл 512 КиБ проходит через настоящие DB и FS UploadCache, с правильным SHA-256 и токеном.
- Link/relink/unlink и очистка нового курсора проверены на настоящем OTRS.
- Обычные комментарии и file-only обновления не создают OTRS заметок; OTRS articles не отправляются как обычная переписка в Redmine. Режимы open/note/open|note, уведомляемые owner/responsible, выбранные файлы, отключённые вложения и archive-фильтр покрыты отдельными Perl-тестами.
- HTTP reuse сохраняет актуальную авторизацию, пересоздаёт клиент при смене настроек и не переносит binary max_size на JSON. TLS ранее проверен с доверенным и недоверенным CA на той же неизменённой версии HTTP.pm; старые результаты сохранены отдельно.

## Проверка установочного пакета

- `Dev::Package::Build` настоящего OTRS собрал OPM из явного каталога исходников.
- Проверены чистая установка 1.0.30, upgrade 1.0.29 → 1.0.30 и reinstall 1.0.30.
- Upgrade сохранил существующие ID полей и связь тикета, пользовательский SyncBatchLimit=37, дополнительное поле карточки и все поля Redmine в TicketZoom; новое служебное поле создано. После чистой установки/переустановки присутствуют все 14 полей моста.
- В OPM **18 файлов** строго из SOPM, permission=644. Каждый декодированный payload совпадает байт-в-байт с текущими исходниками и установленным файлом.
- Тесты, граф, .env, SQL seed, профили и локальные служебные файлы не входят в OPM.
- Пакет пользовательский, без внешней подписи. CloudServices в тестовой среде отключены; опубликованных портов нет. Первый заблокированный внутренней сетью запрос стандартной cloud-проверки исправлен настройкой локального стенда; успешные установки выполнялись без cloud-проверки.

Файл: `dist/OTRSRedmineBridge-1.0.30.opm`. SHA-256: `a1319bdf76fe4ca09a532708c829b668590279de3a210b58ed36e82a695cac7e`. Контрольная сумма также в `dist/SHA256SUMS`.

## Границы проверки и остаточные ограничения

- OTRS 6.0.10 CE / Perl 5.16.3 / MariaDB 10.11, Docker amd64 под эмуляцией на Mac arm64. Znuny 7, нативный production Linux, реальный Redmine и визуальные браузерные сценарии UI здесь не проверялись. Шаблоны и модули UI не изменены; их файлы входят в проверенный пакет.
- CPU/RSS относятся к одному Perl-воркеру, не ко всему OTRS-серверу. База и локальный Redmine HTTP-симулятор не входят в измерения. Email-доставка отключена; формирование получателей проверено Perl-тестами.
- Стандартный UploadCache API читает все дополнительные файлы агрегатом. При конкурентном изменении формы между metadata и data кратковременный пик внутри самого API не гарантируется общим лимитом; изменившийся набор отклоняется до создания задачи, а содержимое не удерживается через сетевые вызовы.
- Дубли заметок при действительно одновременных синхронизациях и неатомарность DF read/set полностью не устранены: это существовавшие до изменений ограничения, а не подтверждение распределённой идемпотентности. Последовательный replay и поздняя запись курсоров покрыты тестами.
- Пакет проверен для обновления с текущей 1.0.29. Обновление с версий со старыми outbound hooks до 1.0.27 не подтверждено и не поддерживается этим ревью.
- Новые лимиты по умолчанию: 5 000 000 байт/файл, 20 000 000 байт/операцию, 20 файлов. Пропуск по входящему лимиту описывается в заметке и продвигает курсор; для пересмотра нужен явный сброс курсора.
