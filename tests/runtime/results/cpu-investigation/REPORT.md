# CPU при создании задачи с вложениями

Дата: 2026-10-12. Все проверки выполнены локально; сервер не изменялся.

## Диагноз

Первоначальный рост CPU на 17% не воспроизвёлся в новой контрольной серии из 18 запусков: медианы исходной версии и первого пакета оптимизаций составили 0.260696 и 0.260324 CPU-секунды. В старой короткой серии были существенные выбросы. Установить точную причину тех двух старых выбросов по сохранённым агрегатным метрикам нельзя.

Профилирование NYTProf с CPU-часами показало, что копирование файлов занимает миллисекунды, а заметная часть времени уходит на сетевой транспорт, холодную загрузку классов OTRS и индексацию внутренней заметки. Каждый из 22 запросов к Redmine создавал новый LWP::UserAgent и соединение. Это подтверждённые повторные расходы, которые можно устранить без накопления содержимого файлов в памяти.

## Изменение

В EscalateTicket введена область жизни HTTP-клиента, ограниченная одной операцией. LWP повторно использует один клиент и одно соединение; по выходу, включая ранний возврат, клиент освобождается. Изменение URL, proxy, timeout или настроек TLS пересоздаёт клиент. API-ключ устанавливается заново для каждого запроса. Ограничение бинарного ответа сбрасывается перед последующим JSON-запросом. Последовательное чтение и отправка файлов, лимиты и функциональность первого пакета сохранены.

HTTP: 15 повторов каждой версии, 45 измерений. HTTPS: 9 повторов каждой версии, 27 измерений. Перед каждой серией выполнено по одному исключённому из статистики прогреву каждой версии. Порядок трёх версий циклически меняется, чтобы каждая одинаково часто занимала каждую позицию. Перед каждым запуском восстанавливается одна база и очищается кеш OTRS. Профилировщик в измерениях выключен.

Относительно первого пакета медианное CPU-время снизилось на 5.3% по HTTP и на 11.3% по HTTPS. Память по HTTP осталась практически прежней. По HTTPS клиент добавил 1.06 МиБ относительно первого пакета, но сохранил 14.83 МиБ выигрыша относительно исходного кода.

Все операции по-прежнему выполняют 22 HTTP-запроса; сокращены соединения с 22 до 1, а не работа или проверяемые данные. После каждой из 72 измеренных операций число открытых соединений равно нулю. SQL: исходная версия 158 запросов, обе оптимизированные — 159; текущая правка SQL не меняет.

Для оценки разброса сохранены попарные bootstrap-интервалы медианного снижения CPU (10 000 выборок, фиксированный seed). HTTP: 3,3–34,0%; HTTPS: 9,0–11,5%. Это другой показатель, чем отношение отдельных медиан в таблице. HTTP-серия шумная; нельзя обещать одинаковый процент ускорения на любом сервере.

## Проверка функциональности

- Perl-тесты: 3 файла, 25 верхнеуровневых subtest, успешно. Добавлены проверки повторного использования соединения, актуального API-ключа, пересоздания при смене timeout, освобождения по выходу и сброса лимита перед JSON.
- Настоящий OTRS: повторно проверены создание задачи, 16 файлов с правильными SHA-256 и прикреплёнными токенами; дополнительный файл UploadCache 512 КиБ; входящие заметки и файлы для 10 связанных тикетов, отсутствие дублей, бинарные байты 00ff8041 и обход 125 тикетов.
- HTTPS: передача всех 16 файлов с проверкой SHA-256 и присоединения токенов. Проверка сертификата включена; отдельный запуск с недоверенным CA отвергнут. Один TLS-клиент на операцию и ноль открытых соединений после неё.

## Методика и границы

OTRS 6.0.10 CE / Perl 5.16.3 / CentOS 7.5, MariaDB 10.11.19. Образ amd64 работает под эмуляцией на Mac arm64. Один OTRS-процесс ограничен одним CPU и 1 ГиБ. Ticket, Article, DynamicField и DB — настоящие службы OTRS. Redmine — контролируемый локальный HTTP/HTTPS-сервер. HTTPS использует временный локальный сертификат с SAN DNS:redmine и явно доверенным CA, без отключения проверки.

CPU измеряется getrusage(RUSAGE_SELF) вокруг операции моста; RSS включает загрузку Perl/OTRS и снимается до проверки результата. Подготовка базы и проверки SHA-256 вынесены из измеряемого участка. CPU/RSS базы данных и сервера Redmine не входят в эти числа. Daemon, cron, почтовые сборщики и web-server OTRS не запускались; email-уведомления отключены. Реальный Redmine и Znuny 7, промышленная параллельная нагрузка и скорость нативного серверного Linux не проверены.

## Данные и воспроизведение

- `reproduction.json`, `reproduction-summary.json`: 18 контрольных запусков до правки CPU.
- `comparison-raw.json`, `comparison-summary.json`: 45 HTTP-измерений.
- `comparison-https-raw.json`, `comparison-https-summary.json`: 27 HTTPS-измерений.
- `profile-before.json`, `profile-pre_cpu.json`, `profile-after.json`: безопасные агрегаты профиля; это отдельные профилированные запуски, не численные результаты ускорения.
- `tls-functional.json`: положительная и отрицательная проверки TLS.
- `../functional.json`: функциональные проверки на реальном OTRS после текущей правки.
- `source-versions.json`: SHA-256 трёх версий и пакета профилировщика; исходный Git commit acc9175b793f405a3ce5431f382ae2da477cbf10.

Скрипт `tests/runtime/cpu_compare.py` запускает сравнение по HTTP; `--tls --repeats 9` запускает HTTPS-серию после подготовки временного сертификата. Предварительно требуется локальный стенд `tests/runtime/run.py --initialize-only` и сохранённые снимки `.state/before`, `.state/pre_cpu`, `.state/after`. Снимок `pre_cpu` проверяется по `pre-cpu-source.json`; не заменяйте его текущим кодом. Эти локальные исходники сохранены, но игнорируются Git. Пароли, SQL seed, приватные ключи и сырые профили не входят в публикуемые результаты; при завершении стенда удаляются. Для полного повторения TLS нужно создать новый сертификат.

В исходном отчёте `../REPORT.md` оставлены первоначальные числа без подмены. Этот отчёт уточняет вывод о CPU на основании расширенных повторных проверок.
