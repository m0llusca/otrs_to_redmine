# Проверка OTRSRedmineBridge на локальном OTRS

Дата: 12 октября 2026 года. Удалённый сервер и рабочие OTRS/Redmine не использовались.

## Результаты замеров

Медианы пяти измеренных повторов каждой версии. CPU — user+system время одного процесса, в секундах; RAM — максимальный RSS этого же процесса, в МиБ. Всего 30 измеренных запусков и 6 исключённых прогревочных.

| Сценарий | CPU до | CPU после | Изменение CPU | RSS до | RSS после | Изменение RSS |
|---|---:|---:|---:|---:|---:|---:|
| Опрос 50 тикетов с одной неизменившейся задачей | 0.389 | 0.231 | -40.6% | 78.31 | 71.47 | -8.7% |
| Одна заметка и два файла по 1 МиБ для каждого из 10 тикетов | 1.945 | 1.237 | -36.4% | 92.50 | 84.87 | -8.2% |
| Создание задачи с 16 вложениями из статьи, суммарно 16 МиБ | 0.261 | 0.304 | +16.7% | 100.48 | 85.79 | -14.6% |

В фоновых сценариях снизились и CPU-время, и пик RSS. При исходящей загрузке память снизилась, но ускорение CPU не подтверждено: медиана выросла на 16.7%, диапазон после изменения составил 0.248–0.534 с против 0.258–0.296 с до изменения. При пяти повторах это нельзя считать устойчивой оценкой поведения под длительной нагрузкой.

## Количество операций

| Сценарий | SQL до → после | HTTP всего до → после | GET задачи до → после | Скачивания файлов до → после |
|---|---:|---:|---:|---:|
| unchanged | 433 → 327 | 53 → 4 | 50 → 1 | 0 → 0 |
| inbound | 681 → 617 | 43 → 7 | 20 → 2 | 20 → 2 |
| outbound | 160 → 161 | 22 → 22 | 3 → 3 | 0 → 0 |

HTTP включает одинаковые запросы прогрева справочников. SQL — разница счётчика Questions той же MariaDB-сессии с исключением запроса измерения; счётчик включает служебные обращения OTRS.

## Проверка результата на настоящих сервисах OTRS

- Созданы 136 синтетических тикетов: 125 для обхода, 10 для входящих заметок и один для исходящих вложений.
- За три прохода старый код посетил 100 уникальных тикетов (50/50/50), новый — все 125 (50/50/25). Это подтверждено чтением сохранённых динамических полей из MariaDB.
- Обе версии отдельно проверены с исходным состоянием `closed successful`: десять тикетов перешли в `open`, каждый получил одну заметку с комментарием и двумя вложениями. Содержимое двадцати вложений совпало по SHA-256. Повторная синхронизация не создала дублей.
- Новая версия отдельно сохранила четыре бинарных байта `00 ff 80 41` в каждом из десяти тикетов без изменений.
- Для исходящих файлов новой версии проверены все 16 SHA-256, размеры, токены в конечном PUT и сохранённая связь задачи в OTRS.
- Дополнительная загрузка через настоящий UploadCache OTRS 6 также проверена: 512 КиБ, правильный SHA-256 и присоединённый токен.

## Среда и методика

- OTRS 6.0.10 CE, Perl 5.16.3, CentOS 7.5 в Docker; MariaDB 10.11.19.
- Mac arm64, образ OTRS amd64 под эмуляцией. Процесс OTRS ограничен одним CPU и 1 ГиБ; одинаково для обеих версий.
- Все Ticket/Article/DynamicField/DB сервисы — настоящие классы OTRS. Никакие тестовые подмены этих сервисов не загружаются. Пути загруженных модулей записаны в raw.json.
- Redmine — контролируемый локальный HTTP-симулятор. Права и поведение настоящего Redmine, TLS и реальные сетевые задержки этим стендом не проверяются.
- Перед каждым измерением восстанавливается один и тот же SQL-снимок и очищается кеш OTRS. Порядок before/after чередуется. Подготовка и проверка результата вынесены за измеряемый участок.
- CPU снимается через BSD::Resource/getrusage(RUSAGE_SELF) до и после операции. Пик RSS включает загрузку OTRS/Perl, но снимается до проверки вложений. CPU и память MariaDB/HTTP-симулятора не входят в эти числа.
- Для измерений входящих заметок тикеты исходно уже находились в open; реальный переход closed successful → open проверен отдельно. Уведомления по email отключены для изоляции; UI и доставка email не проверялись.
- Daemon, cron, почтовые сборщики и веб-сервер не запускаются. Изоляция Docker internal=true, опубликованных портов нет.
- База bridge_benchmark новая; старые локальные базы, контейнеры и их volumes не использовались.

Базовый commit: `acc9175b793f405a3ce5431f382ae2da477cbf10`. Отпечатки исходников и digest образов: source-fingerprints.json. Файл redmine-measured.mjs сохраняет точную версию HTTP-симулятора, использованную для основной серии; расширенная проверка исходящих SHA-256 добавлена после замеров и выполнена отдельно.

## Границы выводов

Это измерения одного OTRS Perl-воркера на синтетической локальной нагрузке. Они не равны памяти всего OTRS-сервера и не предсказывают точные значения на рабочем Linux без эмуляции. Znuny 7 здесь не запускался. Для дополнительных файлов формы API UploadCache по-прежнему читает содержимое агрегатом после проверки общего лимита. Промышленная нагрузка, параллельные агенты и размеры журналов сверх этих сценариев не профилировались.

## Воспроизведение

Из корня репозитория:

```bash
python3 tests/runtime/run.py --baseline acc9175b793f405a3ce5431f382ae2da477cbf10
python3 tests/runtime/verify.py
docker compose -f tests/runtime/compose.yaml stop
```

Скрипты работают только с проектом Docker bridge-perf-local, новой тестовой базой и внутренней сетью. Изменения не отправляются на сервер. Пароли тестового стенда создаются локально в игнорируемом .env с правами 0600.

## Завершение стенда

После получения результатов удалены только контейнеры, внутренняя сеть и новая база проекта `bridge-perf-local`. Существовавшие до проверки контейнеры и volumes не удалялись. Измерения, исходные данные отчёта и отпечатки кода сохранены в этой папке; повторный запуск создаст новую тестовую среду.

## Уточнение CPU после расширенной проверки

Первоначальный рост CPU при создании задачи с вложениями не воспроизвёлся в дополнительной контрольной серии. Повторное использование HTTP-клиента в пределах одной операции снизило медианное CPU-время на 5% по HTTP и 11% по HTTPS относительно первого пакета, сохранив основной выигрыш по памяти. Подробная методика, исходные данные и границы выводов: [CPU investigation](cpu-investigation/REPORT.md). Эти новые результаты дополняют первоначальные числа выше.
