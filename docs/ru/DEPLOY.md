# Установка

Собрать `.opm`, поставить в Package Manager, затем задать SysConfig (или экран Admin).

## Перед установкой

1. Сервисная УЗ Redmine (не личный API-ключ) с правом создавать задачи в целевом проекте.
2. Согласованные `project_id` / `tracker_id`.
3. Сеть от OTRS до Redmine (TLS, proxy, DNS).
   - С хоста OTRS: `curl -vI --max-time 15 https://redmine.example.org/` (ожидается HTTP 200/302, не timeout).
   - TLS: `openssl s_client -connect redmine.example.org:443 -tls1_2 </dev/null` — должен завершиться без `handshake failure`.
   - Если curl/openssl OK, а мост падает на SSL — Admin → TLS diagnostics; при необходимости `Redmine::AllowLegacyTLS` только временно.
   - Если выход только через proxy — SysConfig `WebUserAgent::Proxy`.
4. `Package::AllowNotVerifiedPackages` (или подпись пакета по политике ИБ).
5. **Daemon** должен быть запущен (`otrs.Daemon.pl` или `znuny.Daemon.pl`) — иначе нет sync / retry Redmine → тикет-система.

## Шаги

1. Собрать `.opm` из этого репо (`Dev::Package::Build`).
2. Admin → Package Manager → Install/Upgrade (версия **1.0.0+**).
3. Убедиться, что созданы DF `Redmine*` (включая RetryPayload / LastAttachmentSyncOn). Очередь `Escalation-Redmine` **не нужна** — триггер только меню «Разное».
4. Admin → **OTRS ↔ Redmine Bridge** (предпочтительно) или SysConfig → `Core::Redmine`:
   - `Redmine::BaseURL` / `APIKey` / `ProjectID` / `TrackerID`
   - `Redmine::OTRSBaseURL` = `https://otrs.example.org` (публичный URL, не hostname сервера)
   - `Redmine::AllowedProjectIDs` — проекты, разрешённые для Create (пусто = только ProjectID); Link/relink — любой проект
   - `Redmine::UITimeout` = 5 (не поднимать без нужды)
   - `Redmine::AutoRetry` = **0** до проверки retry payload; включать осознанно
   - `Redmine::SubjectPrefix` = **пусто**
   - `Redmine::Enabled` = `0` до первой проверки
5. Кнопка Admin «Показать поля Redmine в карточке» (или Zoom DF уже мержатся на install).
6. Проверка: Daemon health в Admin → Run sync now; TicketZoom → **Разное** → эскалация/Link; второй клик без дубля issue.
7. Затем `Enabled=1` для нужных агентов + ACL/`Redmine::AgentGroup` при необходимости.

## Синхронизация (с 1.0.27)

Письма и заметки тикета **не** уходят в Redmine после создания/привязки. При привязке/отвязке — только короткая заметка (ссылка на тикет + агент), без штампа моста. Redmine → OTRS нужен Daemon и `Redmine::InboundSync`.

`Redmine::StatusSync` — по одной строке, имя статуса Redmine = состояние OTRS:

| Значение | Эффект |
|----------|--------|
| `open` | Только сменить состояние OTRS |
| `open\|note` | Состояние **и** внутренняя заметка (статус + комментарий из того же журнала) |
| `note` | Только заметка, без смены состояния |

Пример: `Проверка решения = open|note`. Комментарии без такой смены статуса остаются в Redmine.

Что копируется и что нет: [PRODUCT.md](./PRODUCT.md).

## Не делать

- Не коммитить API-ключ.
- Не включать мост всем сразу без ACL и способа выключить (`Enabled=0`).

## Нагрузка и ограничения вложений

Фоновая синхронизация обходит связанные тикеты ограниченными страницами по ID. Позиция обхода хранится в кеше OTRS; после очистки кеша обход начнётся сначала. Архивные тикеты исключаются, когда включена система архивирования OTRS. Для общей задачи Redmine снимок и журнал переиспользуются внутри одной группы тикетов; курсоры каждого тикета остаются отдельными. Неизменившаяся задача требует только компактного GET и обновления времени проверки.

В SysConfig `Core::Redmine` доступны лимиты:

| Настройка | По умолчанию | Назначение |
|---|---:|---|
| `Redmine::MaxAttachmentBytes` | 5 000 000 | Размер одного файла |
| `Redmine::MaxAttachmentTotalBytes` | 20 000 000 | Суммарные байты файлов одной операции создания / входящей заметки |
| `Redmine::MaxAttachmentCount` | 20 | Количество файлов; также ограничивает попытки входящего скачивания |

Превышение общего лимита при создании отклоняется до создания задачи. При входящей синхронизации пропущенные из-за лимита файлы перечисляются во внутренней заметке и считаются просмотренными. Для повторного импорта после изменения лимита потребуется отдельно сбросить курсор вложений. Скачивания прерываются при превышении лимита, бинарные байты не декодируются как UTF-8. Файлы общей задачи временно сохраняются на диск с автоматическим удалением.

Файлы статей OTRS читаются и отправляются по одному. Штатный UploadCache OTRS 6 возвращает дополнительные загрузки только вместе: их общий объём проверяется по метаданным до чтения содержимого. Это ограничение API; полный профиль памяти OTRS всё равно требует замера на установленной системе.

## Локальные проверки

`prove -I tests/lib -I . tests/*.t`

Нужны Perl, Test::More, DBI, DBD::SQLite, JSON::PP, LWP::UserAgent и HTTP::Daemon. Тесты используют подмены границ сервисов OTRS, настоящую SQLite для SQL выборки и локальный HTTP-сервер для транспорта. Они не обращаются к рабочим OTRS/Redmine. Команда `perl tests/performance_counts.pl` выводит число операций для воспроизводимого сценария; это не измерение CPU/RSS продакшена.

При создании или связывании задачи HTTP-клиент повторно использует не более одного соединения в пределах операции и освобождается при выходе. Смена URL, proxy, timeout или настроек TLS создаёт новый клиент; каждый запрос получает актуальный API-ключ. Содержимое вложений по-прежнему обрабатывается по одному файлу. Локальные замеры CPU/RSS и проверка TLS описаны в `tests/runtime/results/cpu-investigation/REPORT.md`.

Версия 1.0.30 создаёт служебное поле `RedmineLastAttachmentSyncOn`: отдельный курсор позволяет безопасно включать синхронизацию файлов после перерыва. После обновления существующие связи один раз получают подробности задачи, затем возвращаются к компактному GET. Файлы формы фиксируются во временных файлах до создания задачи; изменение списка между проверкой метаданных и чтением отклоняется. API UploadCache OTRS 6 возвращает содержимое только агрегатом: при одновременном изменении формы пик внутри этого вызова не гарантирован общим лимитом, хотя изменившийся набор отклоняется до сетевых действий. Ошибка вложения не отменяет смену состояния; неудавшаяся заметка сохраняет курсоры для повторения.

## Синхронизация 1.0.31

Меняется только расширение OTRS: стандартный REST API Redmine используется без webhook и плагинов Redmine. Новый модуль `DaemonModules###RedmineBridgePoller` опрашивает уникальные связанные задачи пакетами до 100 ID. `Redmine::SyncPollInterval` задаёт паузу между проходами (по умолчанию 5 секунд). Это не гарантия мгновенной доставки: HTTP, очередь и массовая рассылка занимают дополнительное время. При 1000 различных задачах один проход требует не менее 10 запросов списка; при 1000 тикетов на одну задачу — одного. Уменьшение задержки относительно старого пятиминутного cron может увеличить частоту запросов Redmine.

Новые таблицы `redmine_sync_issue` и `redmine_sync_lock` в существующей БД OTRS сохраняют обнаруженную версию, прогресс и повторы. Scheduler доставляет обновления порциями до `Redmine::SyncBatchLimit` тикетов (50 по умолчанию), с бюджетом 10 секунд между тикетами; отдельный сетевой вызов может занять дольше. `Redmine::SyncWorkers` ограничивает активные задачи доставки (1 по умолчанию, 1–4). При ошибке или перезапуске продолжение восстанавливается из БД. Старое расписание `Daemon::SchedulerCronTaskManager::Task###95-RedmineBridgeSync` удалено; не добавляйте параллельный внешний cron. После установки/обновления перезапустите штатный Daemon. «Run sync now» обнаруживает изменения и выполняет одну порцию, остальное продолжает Daemon.

Неизменившиеся тикеты не получают технических DF-записей, истории или событий. `RedmineLastSyncAt` больше не создаётся и не обновляется; существующее поле и исторические значения сохраняются при обновлении. Проверки доступны в служебном кеше health. Статусные журналы применяются по ID, включая переход с возвратом к прежнему статусу. Сохраняются `StatusSync |note`, запрет обычных комментариев/file-only заметок, отдельные курсоры тикетов и синхронизация закрытых тикетов. Одинаковый `updated_on` дополнительно проверяется ограниченными запросами подробностей (до двух за проход): недавно изменённые задачи допускают более частую проверку, остальные проходят периодическую сверку; мгновенное обнаружение в этом случае не гарантируется.

HTTP 429/502/503/504 включает общую паузу для этого источника: `Retry-After` учитывается до часа, иначе используется экспоненциальная задержка. Ошибка файла сохраняет незавершённую доставку; один и тот же недоступный файл не скачивается повторно внутри порции одной задачи. Ручная и фоновая синхронизация разделяют блокировку тикета. Создание входящей заметки, DB-вложений и бизнес-курсоров выполняется одной короткой транзакцией после сетевых запросов. Это требует транзакционных таблиц БД. Откат FS-хранилища может оставить неиспользуемые файлы, а внешние действия сторонних немедленных обработчиков событий не откатываются транзакцией БД.

Изменения настроек подхватываются фоновым процессом при штатном пересоздании примерно раз в минуту (после завершения текущего опроса).

Штатные уведомления OTRS отправляются после транзакции. Аварийное завершение процесса между commit и отправкой уведомлений не даёт гарантии доставки уведомления; гарантия отката относится к заметке и DB-курсорам.

Постоянно обновляемая задача не обнуляет курсор активного обхода: после его окончания выполняется повторный обход для уже обработанных тикетов. Очередь выбирает давно обслуживавшиеся задачи среди готовых, чтобы горячая задача или retry не блокировали остальные. Lease и версия активного обхода позволяют завершить медленную загрузку, сохраняя новую обнаруженную версию для следующего прохода.

Ошибка отдельного тикета больше не блокирует остальные: в БД сохраняется первый неудавшийся тикет и курсор обхода, после завершения обход возвращается к ошибке. Успешные заметки защищены собственными курсорами. Промежуточные переходы сохраняются в заметке, а состояние OTRS согласуется только с текущим статусом Redmine, без повторного проигрывания старых open/close при ошибке файла.
